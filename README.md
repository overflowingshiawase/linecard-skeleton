# LINE 電子名片系統 — 個人技術骨架複刻版

> 這是 [LINE電子名片團隊專案] 的個人獨立複刻版本。範圍刻意精簡到最小可行流程，目的是驗證我能否獨立理解並重現團隊專案背後的完整技術鏈路，而非依賴分工只熟悉自己負責的那一小塊。

## 背景

在職訓課程的 5 人團隊專案中，我們用 Next.js + Supabase + LINE LIFF 做出了一套功能完整的電子名片系統（可自訂版型、色彩，掃 QR Code 即用）。專案順利上線後，我認為只熟悉自己分工的那一塊還不夠——**如果連不出自己負責的環節都講不出「為什麼」，就不算真正理解這個系統。**

於是我用團隊版本相同的核心技術棧（FastAPI + Supabase），獨立從零重做了一個範圍精簡的骨架版，目標是能不看筆記、獨立講清楚「使用者填表單 → 資料進資料庫 → 網址查資料 → 圖片為什麼存網址不存檔案 → 分享按鈕做了什麼」這整條資料流。

## 技術棧

- **前端**：原生 HTML / JavaScript（表單頁、fetch API 呼叫）
- **後端**：FastAPI（Python）
- **資料庫**：Supabase PostgreSQL
- **檔案儲存**：Supabase Storage（大頭照）
- **部署**：Railway（GitHub 串接自動部署）
- **版本控制**：Git / GitHub

## 功能範圍（刻意精簡）

| 功能 | 有做 |
|---|---|
| 表單填寫（姓名/職稱/公司） | ✅ |
| 大頭照上傳（存 Supabase Storage） | ✅ |
| 專屬 slug 短網址查詢頁面 | ✅ |
| 一鍵分享至 LINE | ✅ |
| 版型/色彩自訂、LIFF、Messaging API 推播 | ❌（團隊版才有，此版本刻意不做） |

## 系統資料流

1. 使用者填表單並選圖片，前端分兩趟請求送出：先上傳圖片拿到公開網址，再連同文字資料一起送去建立名片
2. 後端用 uuid 為圖片產生不重複檔名，存進 Supabase Storage，資料表只存這張圖片的公開網址（不存檔案本身）
3. 任何人打開 `/card/{slug}` 網址，後端把 slug 當查詢條件去資料庫撈資料，組成 HTML 回傳
4. 分享按鈕組出 LINE 官方分享端點的連結，把名片網址當參數帶過去

## 開發過程中的實戰教訓

- **本機能跑 ≠ 雲端能跑**：部署到 Railway 後因環境變數（Supabase URL / Key）未同步設定，連續 crash 兩次，透過讀取 deploy log 的 Traceback 逐一定位並修復，理解了「設定與程式碼要分離」這個雲端部署的基本原則
- **金鑰安全處置**：開發過程中曾誤將 `.env` 推上 GitHub，處理流程為：立即重新產生（rotate）Supabase 金鑰讓舊金鑰失效、清除 git 歷史紀錄、重建乾淨的 repo。這讓我理解「發現外洩後第一件事是換鎖，不是找鑰匙」
- **前後端脫節**：後端 API 寫好後一度忘記讓前端實際呼叫它，直到端到端測試才發現——學到「前後端各自能動」不等於「系統真的能動」
